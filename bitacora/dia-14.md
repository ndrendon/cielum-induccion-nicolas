## Autoinvestigación básica

1. **Pregunta:** ¿Qué es RPA? Bots atendidos vs no atendidos.

   **Respuesta (con mis palabras):** RPA (*Robotic Process Automation*, automatización robótica de procesos) es usar un programa, llamado bot o robot de software, para que haga en el computador las tareas que haría una persona: abrir aplicaciones, hacer clic, escribir en formularios, copiar datos de una pantalla a otra, leer un Excel o descargar un reporte. El bot trabaja sobre la pantalla de las aplicaciones y repite los mismos pasos que hace la persona. Se usa para tareas repetitivas y con reglas claras, sobre todo en aplicaciones que no tienen una API. Un **bot atendido** trabaja junto a una persona, en su mismo computador y con su sesión abierta. La persona lo inicia cuando lo necesita, por ejemplo con un clic, y está pendiente de lo que hace: después de que la persona entra al sistema, el bot llena y envía un reporte de gastos. Un **bot no atendido** trabaja solo, sin nadie al lado. Lo inicia un horario, un evento o una plataforma que le reparte el trabajo, como Orchestrator en UiPath, y corre en una máquina física o virtual. Se usa para tareas grandes que se hacen en lote y con reglas fijas, por ejemplo revisar todos los reportes de gastos y aprobar los que estén por debajo de un monto. En Power Automate, un flujo no atendido inicia sesión en la máquina por su cuenta, deja la pantalla bloqueada mientras trabaja y cierra la sesión al terminar.

   **Fuente:** <https://learn.microsoft.com/es-es/training/modules/robotic-process-automation/1-introduction> · <https://docs.uipath.com/robot/standalone/latest/admin-guide/attended-automations> · <https://docs.uipath.com/robot/standalone/latest/admin-guide/unattended-automations> · <https://learn.microsoft.com/es-es/power-automate/desktop-flows/run-unattended-desktop-flows>

2. **Pregunta:** ¿Cuándo usar RPA y cuándo una integración por API? Riesgos del RPA (cambios de pantalla, fragilidad).

   **Respuesta (con mis palabras):** Una **integración por API** conecta los sistemas directamente: un programa le manda peticiones a la API del otro sistema y recibe los datos en un formato fijo, como JSON, sin pasar por la pantalla. Es la primera opción cuando el sistema tiene una API o un conector listo, porque la API está hecha para que otros programas la usen: es más rápida, más estable y no se daña cuando le cambian el diseño a la pantalla. La **RPA** se usa cuando no hay otra forma de llegar a los datos: aplicaciones viejas sin API, programas de escritorio o páginas que solo se manejan desde la pantalla, o cuando sí hay API pero no tiene todas las operaciones que están en la pantalla. Los **riesgos** de la RPA vienen de que depende de la pantalla. El bot encuentra cada botón o campo con un selector, que guarda los atributos de ese elemento. Si la aplicación cambia el diseño, el texto de un botón, el orden de los campos o un atributo, el selector ya no encuentra el elemento y el bot falla; por eso se dice que la RPA es frágil. También falla si la página carga más lento de lo normal, si sale una ventana que el bot no esperaba o si se cierra la sesión. Además es más lenta, porque tiene que esperar a que carguen las pantallas, y necesita el usuario y la contraseña de alguien para entrar a las aplicaciones. Por eso un bot necesita mantenimiento: hay que revisar sus errores y arreglarlo cada vez que cambia la aplicación.

   **Fuente:** <https://learn.microsoft.com/es-es/training/modules/robotic-process-automation/1-introduction> · <https://docs.uipath.com/studio/standalone/latest/user-guide/about-selectors> · <https://playwright.dev/docs/locators>

3. **Pregunta:** Herramientas: UiPath, Power Automate Desktop, Automation Anywhere, Robot Framework, Python (Playwright/Selenium, pyautogui).

   **Respuesta (con mis palabras):** **UiPath**, **Power Automate Desktop** y **Automation Anywhere** son plataformas de RPA, donde los bots se arman casi sin escribir código. En UiPath, los flujos se diseñan en **UiPath Studio** arrastrando actividades, como hacer clic, escribir o leer un Excel; el **Robot** los ejecuta, y **Orchestrator** los programa y los reparte entre los robots no atendidos. **Power Automate Desktop** es la herramienta de Microsoft para crear flujos de escritorio en Windows: automatiza aplicaciones de escritorio y web, archivos de Excel, carpetas y aplicaciones viejas, usando los elementos de la pantalla, imágenes o coordenadas. Se puede correr a mano o desde un flujo de nube de Power Automate, en modo atendido o no atendido, y el no atendido necesita el plan Process. **Automation Anywhere** es otra plataforma comercial, con bots atendidos y no atendidos, y además trae herramientas para leer documentos y para descubrir cómo se hacen los procesos. Las otras herramientas son de código. **Robot Framework** es un framework de código abierto, hecho en Python, para pruebas automáticas y RPA: los pasos se escriben con palabras clave (*keywords*) fáciles de leer, y se le agregan librerías, como Browser, que usa Playwright, o SeleniumLibrary. En **Python** también se puede hacer RPA directamente con librerías. **Playwright** y **Selenium** manejan el navegador: abren páginas, llenan formularios, hacen clic y leen datos. **PyAutoGUI** maneja el mouse y el teclado de todo el computador, así que sirve para aplicaciones de escritorio, pero trabaja con coordenadas e imágenes de la pantalla. Trae un seguro: si uno lleva el mouse a una esquina de la pantalla, el programa se detiene.

4. **Pregunta:** ¿Qué es n8n? Nodos, triggers, ejecuciones, credenciales.

   **Respuesta (con mis palabras):** n8n es una herramienta para automatizar procesos conectando aplicaciones y servicios. En lugar de escribir todo un programa, se arma un **workflow** (flujo de trabajo) en un lienzo, uniendo nodos con flechas. Se puede usar en la nube de n8n o instalar en un servidor propio (*self-hosted*), por ejemplo con Docker. Un **nodo** es cada paso del workflow. Hay nodos para conectarse con aplicaciones, como Gmail, Slack o Zoho CRM, un nodo HTTP Request para llamar cualquier API y nodos para trabajar con los datos, como If, Merge o Code. Los datos pasan de un nodo al siguiente como una lista de items, donde cada item es un objeto JSON, y cada nodo normalmente se ejecuta una vez por cada item que recibe. Un **trigger** (disparador) es el nodo que arranca el workflow cuando pasa algo: a una hora (Schedule Trigger), cuando llega una petición a una URL (Webhook), cuando pasa algo en una aplicación, como un correo nuevo, o con un clic para probarlo a mano. Una **ejecución** es cada vez que el workflow corre. Las ejecuciones manuales se lanzan desde el editor para probar, y las de producción se hacen solas cuando el workflow está publicado y se cumple el trigger. Las de producción se revisan en la pestaña **Executions**, donde se ve qué datos pasaron por cada nodo y en cuál falló. Una **credencial** guarda los datos para conectarse a un servicio, como un usuario y una contraseña, una API key o un token de OAuth. Se crea una sola vez, n8n la prueba al guardarla y la guarda cifrada en su base de datos. Los nodos la usan escogiéndola de una lista, sin escribir el secreto dentro del workflow.

   **Fuente:** <https://docs.n8n.io/glossary/> · <https://docs.n8n.io/build/work-with-data/understand-n8ns-data-structure/> · <https://docs.n8n.io/build/understand-workflows/understand-executions/types-of-executions/> · <https://docs.n8n.io/build/understand-workflows/create-and-edit-credentials/>

5. **Pregunta:** Webhooks: qué son y cómo funcionan.

   **Respuesta (con mis palabras):** Un **webhook** es una forma de que un sistema le avise a otro, en el momento, que pasó algo. El sistema que va a recibir los avisos tiene una URL, y en el sistema que avisa se registran esa URL y los eventos que interesan, por ejemplo "se creó un pedido" o "llegó un lead nuevo". Cuando pasa uno de esos eventos, el sistema que avisa manda una petición HTTP, casi siempre un POST, a esa URL, con los datos del evento en el cuerpo, normalmente en JSON. El sistema que recibe procesa los datos y responde rápido con un código 2xx para decir que le llegó; si no responde a tiempo, el que avisa toma la entrega como fallida. Así los datos llegan apenas pasa el evento, sin tener que consultar la API a cada rato para ver si hay algo nuevo (*polling*), y se gastan menos recursos y menos llamadas a la API. Para que sea seguro, la URL debe usar HTTPS y el que recibe debe comprobar que el aviso sí viene de quien dice, por ejemplo con un secreto o una firma. En n8n, el nodo **Webhook** es un trigger que crea esa URL: tiene una URL de prueba, que escucha mientras se prueba el workflow en el editor, y una URL de producción, que funciona cuando el workflow está publicado. Zoho CRM también puede llamar un webhook desde una regla de flujo de trabajo.

   **Fuente:** <https://docs.github.com/es/webhooks/about-webhooks> · <https://docs.github.com/es/webhooks/using-webhooks/best-practices-for-using-webhooks> · <https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/>

## Autoinvestigación avanzada

1. **n8n: expresiones, nodo Code, IF/Switch, Merge, Loop, manejo de errores y Error Workflow.**

   Las **expresiones** sirven para llenar un parámetro de un nodo con datos que cambian en cada ejecución, en lugar de un valor fijo. Se escriben entre llaves dobles, con JavaScript adentro: `{{ $json.email }}` toma el campo `email` del item que llega al nodo, `{{ $('Webhook').item.json.body.nombre }}` toma un dato de otro nodo por su nombre y `{{ $now.toFormat('yyyy-MM-dd') }}` da la fecha de hoy con la librería Luxon, que n8n trae para las fechas.

   El **nodo Code** sirve para escribir código propio en JavaScript o en Python cuando los otros nodos no alcanzan. Tiene dos modos: **Run Once for All Items**, que corre una sola vez con todos los items (`$input.all()`), y **Run Once for Each Item**, que corre una vez por cada item. Devuelve una lista de items, cada uno con su objeto `json`. No puede hacer peticiones HTTP ni leer archivos; para eso están los nodos HTTP Request y Read/Write Files from Disk.

   El **nodo If** revisa una o varias condiciones, unidas con AND u OR, y manda cada item por la salida **true** o por la salida **false**. El **nodo Switch** es para cuando hay más de dos caminos: tiene una regla por cada salida, por ejemplo una para Web, otra para Referido y otra para Evento, y una salida de respaldo (*fallback*) para los items que no cumplen ninguna regla.

   El **nodo Merge** junta los datos de dos o más ramas y espera a que lleguen los datos de todas sus entradas. Puede ponerlos uno detrás de otro (**Append**), unirlos por un campo que coincide en las dos entradas, como un id o un correo (**Combine by Matching Fields**), o unirlos por su posición (**Combine by Position**).

   Para los **loops**, casi todos los nodos ya se ejecutan una vez por cada item, así que pocas veces hay que armar un ciclo. El nodo **Loop Over Items** sirve para procesar los items por grupos (**Batch Size**), por ejemplo de a 10 para no pasar el límite de llamadas de una API: manda cada grupo por la salida **loop** y, cuando termina con todos, entrega el resultado completo por la salida **done**. Entre un grupo y otro se puede poner un nodo **Wait**.

   Para el **manejo de errores**, cada nodo tiene en su pestaña **Settings** la opción **Retry On Fail**, que lo vuelve a intentar si falla, y **On Error**, que dice qué hacer cuando falla: parar el workflow (**Stop Workflow**), seguir con el siguiente nodo (**Continue**) o seguir por una salida de error (**Continue (using error output)**) para manejar el error en otra rama. El nodo **Stop and Error** hace fallar el workflow a propósito cuando se cumple una condición. Un **Error Workflow** es un workflow aparte que empieza con el nodo **Error Trigger** y se escoge en **Workflow Settings → Error workflow** del workflow principal. Cuando una ejecución automática del principal falla, n8n corre el Error Workflow y le pasa el id y la URL de la ejecución, el mensaje de error, el último nodo que se ejecutó y el nombre del workflow; con eso se puede mandar una alerta por correo o por Slack. No corre con las ejecuciones manuales, así que para probarlo hay que publicar el workflow principal.

   **Fuente:** <https://docs.n8n.io/build/work-with-data/transform-data/expressions-for-data-transformation/> · <https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.code/> · <https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.switch/> · <https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.merge/> · <https://docs.n8n.io/build/flow-logic/loop/> · <https://docs.n8n.io/build/flow-logic/handle-errors-gracefully/> · <https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.errortrigger/>

2. **n8n self-hosted en Docker, persistencia y variables de entorno.**

   **Self-hosted** quiere decir instalar n8n en un servidor o computador propio, en lugar de usar la nube de n8n. Con Docker se usa la imagen oficial `n8nio/n8n`: el contenedor publica el puerto 5678 (`-p 5678:5678`) y el editor se abre en `http://localhost:5678`. La documentación recomienda Docker Compose, para dejar en un solo archivo la imagen, el puerto, el volumen y las variables.

   La **persistencia** es que los datos no se pierdan cuando se borra el contenedor o se actualiza la imagen. Por eso se monta un volumen en la carpeta `/home/node/.n8n` del contenedor (`-v n8n_data:/home/node/.n8n`). Ahí n8n guarda su base de datos SQLite, con los workflows, las credenciales y las ejecuciones, y también la llave de cifrado de las credenciales y los logs. Para un uso más serio se puede cambiar SQLite por PostgreSQL con `DB_TYPE=postgresdb` y las variables `DB_POSTGRESDB_HOST`, `DB_POSTGRESDB_PORT`, `DB_POSTGRESDB_DATABASE`, `DB_POSTGRESDB_USER` y `DB_POSTGRESDB_PASSWORD`. Aun así, la carpeta `.n8n` debe seguir en un volumen, porque ahí está la llave de cifrado.

   Las **variables de entorno** configuran n8n sin tocar su código. Se pasan con `-e` en `docker run`, o en `environment` o un archivo `.env` con Docker Compose. Algunas importantes:

   - `GENERIC_TIMEZONE` y `TZ`: la zona horaria, por ejemplo `America/Bogota`, para que el Schedule Trigger corra a la hora de Colombia.
   - `N8N_ENCRYPTION_KEY`: la llave con la que se cifran las credenciales. Si no se pone, n8n crea una al azar la primera vez y la guarda en la carpeta `.n8n`. Si esa llave se pierde, las credenciales guardadas ya no se pueden leer.
   - `N8N_WEBHOOK_URL` (antes `WEBHOOK_URL`): la dirección pública de n8n, para que las URL de los webhooks salgan bien cuando n8n está detrás de un dominio o de un proxy.
   - `N8N_LOG_LEVEL`: cuánto detalle tienen los logs: `error`, `warn`, `info` o `debug`.
   - `N8N_BLOCK_ENV_ACCESS_IN_NODE`: con `true`, el nodo Code y las expresiones no pueden leer las variables de entorno.

   Las variables de la base de datos aceptan el sufijo `_FILE`, por ejemplo `DB_POSTGRESDB_PASSWORD_FILE`, para leer el valor desde un archivo y no dejar la contraseña escrita en el `docker-compose.yml`.

   **Fuente:** <https://docs.n8n.io/deploy/host-n8n/install-options/install-with-docker/> · <https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/database/> · <https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/configuration-examples/set-a-custom-encryption-key/> · <https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/endpoints/> · <https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/set-up-logging/> · <https://docs.n8n.io/deploy/host-n8n/configure-n8n/basic-configuration/use-environment-variables/security/>

3. **Buenas prácticas: idempotencia, reintentos, logs, no exponer credenciales.**

   **Idempotencia:** una operación es idempotente si hacerla una vez o varias veces deja el mismo resultado. En HTTP, GET, PUT y DELETE son idempotentes, y POST no, porque cada POST puede crear un registro nuevo. En una automatización los mismos datos pueden llegar dos veces, por un webhook repetido, por un reintento después de un error de red o porque alguien vuelve a correr el workflow, y si el flujo no es idempotente crea registros duplicados, como dos leads o dos pedidos iguales. Para evitarlo, antes de crear se busca si el registro ya existe por un dato único, como un id o el correo, y si existe se actualiza en lugar de crearlo. A eso se le dice *upsert*, y la API de Zoho CRM lo trae con `POST /crm/v8/Leads/upsert`. Otra forma es guardar el id de cada evento que ya se procesó e ignorar los que lleguen repetidos.

   **Reintentos:** muchos errores son pasajeros: la red se cae un momento, el servicio está ocupado o se pasó el límite de llamadas. Para esos errores conviene volver a intentar, esperando cada vez un poco más y con un número máximo de intentos; si sigue fallando, se trata como un error de verdad y se avisa. Los errores que no se arreglan solos, como datos malos o un token inválido, no se reintentan. Solo es seguro reintentar una operación idempotente, porque si no, el reintento puede repetir lo que ya se hizo. En n8n se configura en cada nodo con **Retry On Fail**, donde se escoge cuántos intentos hacer (**Max Tries**) y cuánto esperar entre uno y otro (**Wait Between Tries**).

   **Logs:** un log es el registro de lo que pasó: cuándo empezó cada ejecución, qué datos procesó, qué falló y por qué. Sirven para encontrar los errores y para saber si algo ya se procesó. En n8n cada ejecución queda guardada con los datos de cada nodo, y los logs del servidor se configuran con `N8N_LOG_LEVEL` y con `N8N_LOG_OUTPUT`, que los manda a la consola o a un archivo. En un reintento conviene registrar los primeros fallos como información y solo el último como error, para no llenar de alertas a quien revisa. Los logs nunca deben tener contraseñas ni tokens.

   **No exponer credenciales:** las contraseñas, los tokens y las API keys no se escriben en el código, en los parámetros de los nodos ni en el repositorio. En n8n van en **Credentials**, que se guardan cifradas, y en Docker van en variables de entorno o en archivos con el sufijo `_FILE`, con el archivo `.env` en el `.gitignore`. Antes de compartir un workflow exportado hay que revisar el JSON, porque trae los nombres y los ids de las credenciales, y un nodo HTTP Request armado desde un cURL puede traer el token en los headers. Cada credencial debe tener solo los permisos que necesita, y se debe cambiar cada cierto tiempo o apenas se filtre.

   **Fuente:** <https://developer.mozilla.org/en-US/docs/Glossary/Idempotent> · <https://learn.microsoft.com/es-es/azure/architecture/patterns/retry> · <https://www.zoho.com/crm/developer/docs/api/v8/upsert-records.html> · <https://docs.n8n.io/build/understand-workflows/workflow-components/work-with-nodes/> · <https://docs.n8n.io/deploy/host-n8n/keep-n8n-running/set-up-logging/> · <https://docs.n8n.io/build/manage-workflows/export-and-import/> · <https://cheatsheetseries.owasp.org/cheatsheets/Secrets_Management_Cheat_Sheet.html>

4. **RPA con Playwright: selectores robustos, esperas, capturas en error.**

   Playwright es una librería para manejar el navegador con código, en JavaScript, Python, Java o .NET. Se hizo para pruebas, pero sirve para RPA en páginas web: entrar con un usuario, llenar formularios, hacer clic, descargar archivos y leer datos de la pantalla.

   **Selectores robustos:** el bot tiene que encontrar siempre el mismo elemento, aunque la página cambie un poco. Playwright recomienda buscar los elementos por lo que ve el usuario, con sus localizadores: `page.getByRole('button', { name: 'Ingresar' })` por el rol y el nombre, `page.getByLabel('Correo')` por la etiqueta del campo, y también `getByPlaceholder`, `getByText` y `getByTestId`, que busca el atributo `data-testid` puesto a propósito para la automatización. No recomienda los selectores CSS o XPath que dependen de la estructura de la página, como `div > div:nth-child(3) > button`, porque esa estructura cambia seguido. Además, los localizadores son estrictos: si encuentran más de un elemento, fallan en lugar de hacer clic en el que no era. Con `npx playwright codegen` se graba lo que uno hace en la página y Playwright propone los localizadores.

   **Esperas:** Playwright espera solo. Antes de hacer clic o escribir, revisa que el elemento sea uno solo y que esté visible, quieto, habilitado y pueda recibir el clic; si eso no pasa dentro del tiempo límite, falla con un `TimeoutError`. Para esperar un resultado se usan las aserciones que reintentan, como `await expect(page.getByText('Pedido creado')).toBeVisible()`, o `page.waitForURL('**/pedidos')` para esperar el cambio de página. No conviene usar esperas fijas como `page.waitForTimeout(5000)`: si la página tarda más, el bot falla igual, y si tarda menos, se pierde tiempo.

   **Capturas en error:** cuando el bot falla, una captura muestra en qué pantalla estaba y qué veía. En un script de RPA, los pasos van dentro de un `try/catch`, y en el `catch` se toma la captura con `await page.screenshot({ path: 'errores/fallo.png', fullPage: true })` antes de cerrar el navegador, y se escribe el error en el log. Con Playwright Test se configura en `playwright.config` con `screenshot: 'only-on-failure'`, y con `trace: 'retain-on-failure'` se guarda una traza para ver paso a paso qué hizo el bot. La captura no debe mostrar contraseñas ni otros datos sensibles.

   **Fuente:** <https://playwright.dev/docs/locators> · <https://playwright.dev/docs/actionability> · <https://playwright.dev/docs/best-practices> · <https://playwright.dev/docs/screenshots> · <https://playwright.dev/docs/api/class-testoptions>

- Qué es la RPA, la diferencia entre los bots atendidos y los no atendidos, y por qué conviene usar una API cuando existe: un bot que trabaja sobre la pantalla falla cuando la aplicación cambia.

La lee `vite.config.js` para pasarle a la API las peticiones que empiezan por `/api`, y el navegador siempre llama a `/api`. Como esa variable la usa Vite y no el código del navegador, no necesita el prefijo `VITE_`: Vite solo deja llegar al navegador las variables que empiezan por `VITE_`, y ahí se leen con `import.meta.env`.
